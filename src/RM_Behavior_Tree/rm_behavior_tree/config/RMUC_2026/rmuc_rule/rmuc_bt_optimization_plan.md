# RMUC 哨兵行为树优化方案（按优先级）

## 目标

本文基于 `rmuc_rule.md` 与当前 `rmuc_2026.xml` / 子树结构，整理一份**按优先级排序**的优化方案，目标是让 RMUC 哨兵行为树更贴近 2026 规则，并具备可落地、可验证、可迭代的实现路径。

> **分工说明**：裁判系统协议解析由电控负责，行为树侧的任务是**定义好需要哪些话题和 msg 字段**，与电控约定接口后直接订阅使用。地图坐标参数在赛前实测填入即可，优先级最低。

## 分析基线

### 已有基础

当前行为树已经具备以下骨架能力：

- 感知与黑板更新：`PerceptionAndBlackboard`
- 主命令输出：`CommandHub`
- 死亡 / 复活恢复：`RespawnRecovery`
- 危急生存：`CriticalSurvival`
- 基地防御：`BaseDefense`
- 交战：`EngageCombat` + `CombatLoop`
- 后勤补给：`SustainAndEconomy` / `HealPlan` / `AmmoPlan`
- 目标控制：`ObjectivePlanner`

### 当前明显缺口

结合规则与 XML，可以看到下面这些问题最影响实战收益：

1. **电控→行为树的话题/msg 接口不完整**：大量裁判系统高价值字段（占领状态、增益值、堡垒储备弹量、敌方易伤、当前姿态反馈、立即复活价格等）还没有通过话题暴露给行为树。行为树侧需要先把需求清单定好，和电控约定 msg 结构。
2. **规则优势还没有完全转成状态机**，尤其是：脱战、虚弱解除、补给区回血窗口、堡垒收益、姿态收益衰减。
3. **经济系统还不够精细**，当前更像"能买就买"，缺少时机与收益比决策。
4. **目标控制优先级偏粗**，对高地 / 堡垒 / 前哨站 / 基地护甲展开的切换还不够规则驱动。
5. **姿态系统虽然有命令接口，但缺少完整战术闭环**。
6. **`WeaknessRecovery.xml` 已存在但未接入主树**，虚弱恢复仅在 `RespawnRecovery` 内处理。
7. **地形跨越增益完全缺失**，没有任何子树或配置支持按序列通过地形跨越增益点。
8. **前哨站重建逻辑完全缺失**，规则允许哨兵连续 10 秒刷卡重建前哨站（前哨站存活 → 基地无敌）。
9. **累计立即复活次数未跟踪**，导致无法评估复活读条螺旋惩罚。
10. **地图坐标仍大量是 `0.0`**，很多战术虽然有树，但实际上无法落地（赛前实测填入即可，不紧急）。

## 优先级总览

| 优先级 | 方向 | 核心目标 |
| --- | --- | --- |
| P0 | 与电控约定话题 / msg 接口 | 让行为树能拿到裁判系统的全部高价值数据 |
| P1 | 生存/复活/虚弱规则闭环 | 保证不会因为规则理解不完整而白给 |
| P2 | 经济与补给决策优化 | 让金币、补血、补弹、立即复活更划算 |
| P3 | 目标控制与区域收益优化 | 让哨兵更会抢点、更会守点 |
| P4 | 姿态、火力与节奏优化 | 让交战收益最大化 |
| P5 | 可观测性与自动迭代能力 | 让后续调优可复盘、可数据驱动 |
| P6 | 地图坐标参数配置 | 赛前实测填入，让导航子树真正可用 |

## P0：与电控约定话题 / msg 接口

### 为什么优先级最高

后续 P1-P4 的所有策略升级都依赖裁判系统数据。协议解析由电控负责，但**行为树侧必须先定义清楚需要哪些话题和字段**，越早约定，电控越早发布，行为树越早可以开发和测试。

`PerceptionAndBlackboard` 当前订阅了以下话题：

### 约定方式建议

1. 行为树侧输出一份 **msg 需求清单**（即上表），标注字段名 + 类型 + 更新频率 + 来源协议
2. 电控侧按需求清单定义 `.msg` 文件，在 `sp_msgs` 或独立包中维护
3. 双方约定话题名和命名空间（仿真带 ns，实车不带）
4. 电控发布话题后，行为树侧在 `PerceptionAndBlackboard` 新增对应的 `Sub*` 节点和 `ParseSentryBlackboard` 字段

### 验证标准

- 每个新话题可以通过 `ros2 topic echo` 确认数据正确
- 仿真环境中有对应的 mock publisher 可供测试
- msg 文件有注释说明每个字段的来源协议和位定义

## P1：生存 / 复活 / 虚弱规则闭环

### 规则依据

`rmuc_rule.md` 明确了几件关键事：

- 脱战定义：**连续 6 秒未发射弹丸且未被扣血**。
- 远程回血：只能在**脱战**时使用。
- 读条复活后：
	- 仅恢复 10% 血量
	- 会进入**虚弱状态**
	- 虚弱时不能占点、不能重建前哨站
- 虚弱解除需要检测到可占领点卡。
- 立即复活有金币成本，但收益更高。

### 当前问题

现有树已经有：

- `RespawnRecovery`
- `IsWeakness`
- `DecideRespawnCmd`

但还缺少完整的战术级闭环：

1. **死亡后是否立即复活**缺少收益模型。
2. **读条复活后的 30 秒无敌窗口**没有被主动利用。
3. **虚弱解除目标选择**目前偏单一，主要往补给区走，但规则允许前哨站 / 基地增益点解除。
4. **脱战状态**虽然有黑板字段，但没有明显看到它对战斗开火 / 脱离决策形成主导约束。

### 优化建议

#### 1. 立即复活决策器升级

把 `DecideRespawnCmd` 从“能不能复活”升级为“值不值得立刻复活”，判断维度至少包含：

- 比赛剩余时间
- 当前金币
- 基地血量与威胁等级
- 当前是否处于关键防守窗口
- 复活后最近可解除虚弱点距离

建议策略：

- **基地高威胁 + 剩余时间少**：倾向立即复活
- **基地安全 + 金币紧张 + 读条很短**：倾向正常复活
- **复活后无法快速解除虚弱**：降低立即复活优先级

#### 2. “复活后无敌窗口”战术利用

新增一个短生命周期状态：`respawn_invincible_window`。

作用：

- 复活后优先快速穿过危险区域
- 复活后优先冲最近解除虚弱点
- 若基地受威胁，可在无敌窗口内更积极回防卡位

#### 3. 虚弱解除路径优化

新增“解除虚弱目标选择器”，候选点不是只有补给区，而是：

- 基地增益点
- 前哨站增益点
- 补给区增益点

按**路径距离 + 当前威胁 + 后续收益**综合选择。

#### 4. 脱战状态接管远程回血条件

将 `state.disengaged` 作为以下决策的硬门槛之一：

- 远程回血
- 远程补弹
- 主动脱离战斗后的补给路线选择

#### ⚠ 补充 5：复活读条速度感知——补给区 4 倍 vs 基地血量 < 2000 时 4 倍

规则明确：复活读条默认 1/s，但在**补给区增益点**或**己方基地血量低于 2000** 时读条速度提高为 **4/s**。这意味着：

- 如果基地血量 < 2000，**无论哨兵在哪里**读条都是 4 倍速，此时可以不急于去补给区
- 如果基地血量 ≥ 2000，只有在补给区才能 4 倍速读条

当前 `DecideRespawnCmd` 和 `RespawnRecovery` 没有利用这个区分。建议：
- 当基地血量 < 2000 时，读条复活本身已经很快，可以降低立即复活优先级（省金币）
- 当基地血量 ≥ 2000 且不在补给区时，读条很慢，应提高立即复活倾向

#### ⚠ 补充 6：复活读条公式与立即复活次数的螺旋惩罚

$$
所需复活读条 = 10 + \frac{420 - 比赛剩余时长}{10} + 20 \times 累计兑换立即复活次数
$$

每次使用立即复活，后续所有读条复活都会多 20 秒。这是**螺旋累积惩罚**。当前 `DecideRespawnCmd` 没有看到 `累计立即复活次数` 输入——需要在黑板中跟踪此值，并作为立即复活收益评估的长期成本。

#### ⚠ 补充 7：立即复活的 4 秒底盘功率翻倍窗口

规则第 4 页：立即复活后底盘功率上限提高 1 倍（不超过 200W），持续 4 秒。这是一个**短暂的机动爆发窗口**，可以用于：
- 快速脱离出生点
- 快速到达关键防守点
- 快速穿越危险区域

当前行为树没有利用这个窗口。建议在立即复活后的前 4 秒内选择更激进的导航目标。

#### ⚠ 补充 8：虚弱解除后的无敌状态切换规则

规则第 4 页的复杂细节：读条复活后无敌 30 秒，但虚弱解除时：
- 如果无敌已累计超过 10 秒 → 无敌立即解除
- 如果未满 10 秒 → 无敌保持到满 10 秒后解除

这意味着：**越快解除虚弱，无敌窗口保留时间越长**。如果 5 秒内解除虚弱，还能保留 5 秒无敌。建议 `WeaknessRecovery` 的目标选择更加强调路径最短而非收益最优。

#### ⚠ 补充 9：`WeaknessRecovery.xml` 未被主树引用

当前 `rmuc_2026.xml` 的 `include` 列表中没有 `WeaknessRecovery.xml`，主树 `ReactiveFallback` 也没有 `WeaknessRecovery` 子树。虚弱恢复目前仅在 `RespawnRecovery` 中处理（导航补给区刷卡），但 `RespawnRecovery` 只覆盖"死亡→复活→恢复"路径。

如果哨兵在**未经历死亡**的情况下进入虚弱状态（理论上不应出现，但需要防御性处理），或者 `RespawnRecovery` 的恢复流程在刷卡前被打断，`WeaknessRecovery` 作为独立子树应该被接入主树作为安全网。

### 验证标准

- 死亡后不会固定采用单一复活策略。
- 读条复活与立即复活的触发时机能解释清楚。
- 虚弱解除不再只会回补给区，而是能择优选最近可解除点。
- 脱战 6 秒规则在日志里可观测、可验证。
- 累计立即复活次数在黑板中有跟踪，且影响后续决策。
- 复活后的无敌窗口 / 功率倍增窗口在日志中可观测。

## P2：经济与补给决策优化

### 规则依据

RMUC 哨兵的经济系统收益非常大：

- 远程回血
- 远程兑换允许发弹量
- 立即复活
- 补给区每分钟 100 发累计获取
- 堡垒区还能提供储备允许发弹量

### 当前问题

当前 `SustainAndEconomy` 只有：

- `HealPlan`
- `AmmoPlan`

再加 `CommandHub` 中的 `DecideEconomyCmd`。

但从结构上看，当前更偏“条件触发”，仍缺少：

1. **金币预算分层**
2. **回血 vs 补弹 vs 立即复活的收益排序**
3. **补给区免费周期弹量的时间感知**
4. **堡垒储备弹量与自身弹量的联动意识**

### 优化建议

#### 1. 引入金币预算器

建议按用途把金币预算拆成三层：

- **生存预算**：立即复活、远程回血
- **持续作战预算**：远程补弹
- **机会预算**：大能量机关 / 高价值抢点窗口

避免出现“前期乱买弹，后期没钱复活”的情况。

#### 2. 引入补给周期意识

补给区每 1 分钟可以给哨兵 100 发允许发弹量，且可累计。建议新增：

- `next_supply_tick_eta`
- `supply_tick_backlog`

策略上：

- 若距离下一个补给 tick 很近，优先去补给区而不是远程买弹
- 若 backlog 很大，补给区价值要显著抬升

#### 3. 远程回血触发更保守

建议远程回血只在同时满足以下条件时触发：

- 处于脱战状态
- 当前血量低于战斗安全阈值
- 预计 6 秒内不会再次卷入交战
- 金币预算允许

#### 4. 立即复活和补弹统一进收益函数

建议建立统一评分：

$$
score = 生存收益 + 守点收益 + 输出收益 - 金币机会成本
$$

这样就不会出现互相打架的局部判断。

### 验证标准

- 远程回血不会在高交战风险时乱开。
- 弹药不足时会优先利用补给区免费收益，而不是无脑远程兑换。
- 金币消耗结构能在赛后复盘中解释。

### ⚠ 补充规则细节

#### 补充 1：远程兑换血量的动态成本公式

远程回血金币成本是动态的：

$$
cost = 50 + \operatorname{ROUNDUP}\left(\frac{420 - 比赛剩余时长}{60} \times 20\right)
$$

开局 50 金币 / 次，末尾涨到约 190 金币 / 次。**越晚远程回血越贵**。当前 `DecideEconomyCmd` 接收了 `stage_remain_time`，但优化档案没有点明这个公式对策略的影响——应该在前期更积极使用远程回血，后期转为物理回补给区。

#### 补充 2：远程兑换弹量 vs 非远程兑换的成本差 15 倍

- 远程兑换：150 金币 / 100 发
- 非远程兑换（补给区/基地增益点/前哨站增益点）：10 金币 / 10 发（等价 100 金币 / 100 发）

但更关键的是：**远程兑换有 6 秒延迟才生效**，且必须处于脱战状态。非远程兑换即时生效。当前 `AmmoPlan` 已经会去最近的补给站，但没有体现"远程兑换延迟 6 秒"对紧急补弹的限制。

#### 补充 3：`0x0120` 指令的单调递增约束

规则第 39 页：`bit2-12` 兑换发弹量值必须**单调递增**，`bit13-16` 远程兑换次数必须**单调递增且每次仅增 1**。这不是策略层面的问题，但如果 `SentryCmdMux` 实现不正确，兑换会失败。需要在验证标准中确认底层协议实现的正确性。

#### 补充 4：金币收入节奏感知

规则表 5-5 显示金币每分钟 +50，但最后一分钟（00:59）是 +150，是平时的 3 倍。这意味着：
- 最后 1 分钟的金币爆发可以用于关键时刻的立即复活或紧急远程回血
- 如果在 01:30 左右还有约 50 金币，1 分钟后会变成 200 金币——此时可以更保守等待收入

当前 `DecideEconomyCmd` 没有感知金币收入节奏。

#### 补充 5：堡垒储备弹量的精确公式

堡垒储备弹量上限：

$$
N = 100 + 2 \times \left\lfloor \frac{\Delta}{15} \right\rfloor, \quad N \le 500
$$

其中 $\Delta$ = 基地血量上限 - 当前基地血量。当 $\Delta = 3000$ 时 $N = 500$。

**前提**：需要 P0 第二批话题中的 `projectile_allowance.fortress_ammo`（`0x0208` offset 6）已由电控发布。如果哨兵在堡垒，发射弹丸优先消耗储备弹量而非自身弹量——这对弹药决策有重大影响（在堡垒打完免费弹再离开）。

## P3：目标控制与区域收益优化

### 规则依据

从规则看，RMUC 的高收益点主要包括：

- 基地增益点
- 中央高地增益点
- 梯形高地增益点
- 地形跨越增益点
- 前哨站增益点
- 补给区增益点
- 堡垒增益点

这些点不是“谁近去谁”，而是要结合：

- 当前血量 / 热量 / 弹量
- 基地是否危险
- 前哨站是否存活
- 比赛前中后期
- 己方基地损血量（影响堡垒收益）

### 当前问题

`ObjectivePlanner` 当前是单个 `SelectObjective` + `SendGoal` + `HoldObjective` 的线性模式，问题是：

1. 候选目标层级不够细。
2. 对比赛阶段转换（前期抢点 / 中期守点 / 后期搏命）体现不够。
3. 没体现“堡垒收益随着基地损血增加而提升”。
4. 没体现“前哨站被击毁后，对方前哨站增益点可占”的特殊窗口。

### 优化建议

#### 1. 目标选择器从单层变成多阶段评分器

建议目标评分拆成：

- **生存收益**
- **经济收益**
- **防御收益**
- **输出收益**
- **路径风险**

#### 2. 引入阶段化目标策略

建议按时间拆分：

- **开局期**：优先中央高地 / 梯形高地 / 补给节奏位
- **中盘期**：优先堡垒、前哨站增益点、基地周边防守
- **残局期**：优先基地防守、关键补血、立即复活收益最大化

#### 3. 强化堡垒策略

堡垒是 RMUC 哨兵的关键优势点，建议单独做一个 `FortressPolicy`：

- 己方基地缺血越多，己方堡垒收益越高
- 对方前哨站被击毁 + 比赛进行 3 分钟后，可考虑敌方堡垒施压
- 但应避免在己方基地危险时远离家门

#### 4. 地形跨越点不要只当路过点

建议把飞坡 / 高地 / 公路 / 隧道增益纳入路径规划收益，而不是仅在到达目标时顺带经过。

### 验证标准

- `SelectObjective` 输出目标不再单一固定。
- 不同时段能明显切换不同目标偏好。
- 堡垒在基地残血时会被主动抬高优先级。

### ⚠ 补充规则细节

#### 补充 1：各增益点防御增益数值汇总表（当前树未量化利用）

| 增益点 | 防御增益 | 附加效果 |
| --- | --- | --- |
| 基地增益点 | 50% | 可兑换弹量 + 解除虚弱 |
| 梯形高地 | 50% | 仅己方可占 |
| 堡垒增益点（己方占） | 50% | + 热量冷却增益 + 储备弹量 |
| 中央高地 | 25% | 排他占领（占了对方不能占） |
| 前哨站增益点 | 25% | 可兑换弹量 + 解除虚弱 |
| 地形跨越（隧道） | 50%，持续 10s | + 2 倍热量冷却 120s |
| 地形跨越（飞坡/高地） | 25%，持续 30s | 叠加同类可到 50% |
| 地形跨越（公路） | 25%，持续 5s | 15s 不可重复获取 |

当前 `SelectObjective` 只有粗糙的优先级，没有量化利用这些防御增益数值差异。基地增益点和梯形高地都是 50%，但基地增益点还能兑换弹量和解除虚弱，综合价值更高。

#### 补充 2：中央高地的排他性占领规则

规则："若一方机器人占领中央高地增益点，另一方机器人无法同时占领"。这意味着中央高地是**争夺资源**——占领它不仅给自己 25% 防御，还**剥夺对方占领权**。`SelectObjective` 应该在敌方占领中央高地时主动争夺。

**前提**：需要 P0 第三批话题中的 `field_status.central_highland`（`0x0101` bit7-8）已由电控发布，提供中央高地占领状态（`1` 己方占领、`2` 对方占领）。

#### 补充 3：前哨站重建机制——哨兵可参与

规则："英雄、步兵、哨兵机器人通过连续检测己方前哨站增益点 RFID 卡 10 秒即可重建前哨站"（比赛开始 5 分钟内）。重建后前哨站恢复 750 血量。**每损失 1000 基地血量获得 1 次重建机会**。

当前行为树完全没有前哨站重建逻辑。考虑到前哨站存活时基地无敌，重建前哨站是极高价值行为。建议在 `ObjectivePlanner` 中加入：
- 己方前哨站被击毁 + 有重建机会 + 比赛 < 5 分钟 → 前哨站增益点优先级极高
- 到达后需要连续停留 10 秒（`HoldObjective` 需要支持此场景）

#### 补充 4：前哨站存活 → 基地无敌的战略价值

规则："当一方前哨站存活，基地处于无敌状态"。这直接意味着：
- 己方前哨站存活时，不需要担心基地被攻击 → 可以更激进
- 己方前哨站被击毁后，基地才可被攻击 → 需要更注重防守
- 对方前哨站被击毁后，对方基地才可被攻击 → 进攻窗口打开

当前 `outpost_alive` 已经在黑板中，但只在 `SelectObjective` 中使用。建议将其纳入 `BaseDefense` 的触发条件——前哨站存活时可以降低 `IsBaseThreatened` 的敏感度。

#### 补充 5：对方堡垒占领 20s 触发基地护甲展开

规则："正在占领对方堡垒增益点的机器人获得 100% 易伤；当一方机器人单次占领时间计满 20 秒，对方基地护甲展开"。

这是一个**高风险高回报**的进攻手段——占领对方堡垒 20s 就能打开对方基地护甲。但期间自身 100% 易伤。需要：
- 确认对方前哨站已被击毁 + 比赛 > 3 分钟
- 评估自身血量是否足够承受 20s 易伤
- 护甲展开后易伤解除

当前行为树完全没有"进攻对方堡垒"的策略分支。

#### 补充 6：`0x0101` 位字段解析不完整

**前提**：需要 P0 第三批话题中以下 `0x0101` 关键字段已由电控发布（当前行为树尚未使用）：

- `bit7-8`：己方中央高地占领状态
- `bit9-10`：己方梯形高地占领状态
- `bit25-26`：己方堡垒增益点占领状态（己/对方/双方）
- `bit27-28`：己方前哨站增益点占领状态
- `bit29`：己方基地增益点占领状态

这些占领状态直接影响目标评分——如果己方已经占领某增益点，就不需要再去占；如果对方正在占领，可能需要争夺。

#### 补充 7：对方敌人标记/易伤信息未利用

`0x020C` 提供了对方各机器人的**易伤状态**和己方机器人的**特殊标识情况**。当对方机器人处于易伤状态时，攻击收益更高。当前 `SelectBestTarget` 只按距离选择目标，没有考虑目标是否易伤。

#### 补充 8：己方队友位置信息未利用

`0x020B` 提供了己方英雄、工程、3 号步兵、4 号步兵的位置坐标。当前行为树完全没有利用队友位置信息。可用于：
- 判断队友是否在基地附近（有人防守则哨兵可以更激进）
- 判断队友是否在某增益点（不需要重复占领）
- 协同：队友在进攻时提供火力支援

## P4：姿态、火力与节奏优化

### 规则依据

RMUC 哨兵姿态系统非常关键：

- 进攻姿态：偏高热量冷却、易伤
- 防御姿态：偏高防御、低冷却
- 移动姿态：偏高机动、易伤
- 姿态切换有 5 秒冷却
- 单姿态累计超过 3 分钟会衰减

### 当前问题

`CommandHub` 中已有 `DecidePosture`，注释里也写了“5s cooldown & 3min degradation policy inside node”，说明底层考虑了规则；但从树结构看，还缺：

1. **姿态与任务没有完全绑定**。
2. **姿态与热量 / 血量 / 路径风险的关系没有外显**。
3. **火力窗口没有充分结合补弹、冷却、姿态收益**。

### 优化建议

#### 1. 姿态与任务绑定

建议形成默认映射：

- `BaseDefense` → 默认防御姿态
- `EngageCombat` → 默认进攻姿态
- `CriticalSurvival` / 转点 / 补给 → 默认移动姿态

在此基础上再由 `DecidePosture` 微调。

#### 2. 增加姿态滞回机制

不要让姿态因为血量和目标抖动频繁切换。建议加入：

- 最小保持时间
- 姿态切换收益阈值
- 任务优先级压制

#### 3. 火力窗口从“能打”升级为“值得打”

当前 `IsFireWindowOk` 更像安全阈值判断。建议升级为综合判断：

- 目标质量
- 当前姿态
- 热量剩余
- 弹量
- 是否正在补给 / 转点关键阶段

### 验证标准

- 姿态切换频率稳定，不会来回抖动。
- 防守、进攻、移动三类任务的姿态选择更符合直觉。
- 热量管理与姿态收益一致。

### ⚠ 补充规则细节

#### 补充 1：姿态衰减的精确影响——3 分钟后收益下降幅度

| 姿态 | 衰减前 | 衰减后 | 损失 |
| --- | --- | --- | --- |
| 进攻 | 3 倍冷却 + 50% 功率 + 25% 易伤 | **2 倍冷却** + 50% 功率 + 25% 易伤 | 冷却倍率 -33% |
| 防御 | 50% 防御 + 50% 功率 + 1/3 冷却 | **25% 防御** + 50% 功率 + 1/3 冷却 | 防御减半 |
| 移动 | 1.5 倍功率 + 25% 易伤 + 1/3 冷却 | **1.2 倍功率** + 25% 易伤 + 1/3 冷却 | 功率加成 -60% |

衰减影响最大的是**防御姿态**（防御直接减半）和**移动姿态**（功率加成大幅下降）。进攻姿态衰减相对最小（3 倍→2 倍冷却仍然很强）。

策略启示：
- 如果需要长时间防守，应考虑在 3 分钟到达前切出防御姿态再切回，重置计时
- 进攻姿态即使衰减后仍是最佳输出姿态，可以更大方地使用
- 移动姿态衰减后功率加成很小（1.2 倍），不应长期使用

#### 补充 2：姿态与堡垒/大能量机关增益的乘算关系

规则示例明确了计算顺序：先算增益（取最大），再乘姿态系数。防御姿态下冷却 ×1/3，进攻姿态下冷却 ×3。

自动哨兵基础冷却 30/s：
- **进攻姿态 + 堡垒冷却增益 75/s**：max(30×3, 30+75) = max(90, 105) → 105... 但规则说"先取较大再乘姿态"，所以实际是 (30+75)×3 = 315 还是 30+75=105？

根据规则第 24 页示例：先在增益和倍率中取较大者（+75），得到 30+75=105，然后乘防御姿态系数 1/3 = 35。所以姿态系数是最后乘的。

进攻姿态下：(30+75) × 3 = **315/s**（极高冷却），这使得进攻姿态 + 堡垒是最强输出组合。

#### 补充 3：`0x0204` 增益字段未完全利用

`0x0204` 直接给出了当前的：回血增益%、射击热量冷却增益值、防御增益%、负防御增益%、攻击增益%。

这些是**裁判系统实时计算后的结果值**，行为树可以直接读取而不必自己推算。**前提**：需要 P0 第二批话题中的 `robot_buff.*`（`0x0204`）已由电控发布。接入后，`DecidePosture` 就可以基于实际增益值而非理论值来决策，更准确。

#### 补充 4：`0x020D` 附加状态字段可读取当前姿态

**前提**：需要 P0 第一批话题中的 `sentry_status.current_posture`（`0x020D` bit12-13）已由电控发布，直接返回哨兵当前姿态（1 进攻 / 2 防御 / 3 移动）。接入后，`DecidePosture` 可以读取裁判系统的真实姿态反馈，避免内部维护状态与实际不同步。

#### 补充 5：`CombatLoop` 没有考虑底盘功率限制

进攻姿态和防御姿态都会将底盘功率降为 1/2（50W），只有移动姿态保持或提升功率。当前 `CombatLoop` 的 `chassis_spin="True"` 在进攻姿态下会因为功率不足导致小陀螺效果大打折扣。建议 `CombatLoop` 根据当前姿态调整底盘策略。

#### 补充 6：云台手操作的 50 金币成本

规则：自动哨兵的云台手每进行一次操作需花费 50 金币。这意味着应尽量减少需要云台手介入的操作（行为树自主完成），否则每次介入都是 50 金币损失。当前行为树已经自主处理大部分操作，但如果有需要人工 fallback 的场景，应该在文档中说明代价。

   - 固定资源点（补给区、基地增益点等）
   - 防守锚点（base_defense_x/y 等）

   - 交战预备点
3. 把 `arrive_radius`、`enemy_near_base_radius`、`objective_hold_ms` 也一起转成地图相关配置

#### ⚠ 地形跨越增益点——有序路径设计

当前 `InitSentryConfig` 完全没有配置**地形跨越增益点**坐标，但规则明确了大量关键地形点位：

- 己方/对方 **公路**（下方 + 上方，共 4 点）
- 己方/对方 **飞坡**（前 + 后，共 4 点）
- 己方/对方 **中央高地**（下方 + 上方，共 4 点）
- 己方/对方 **隧道**（一端 + 中间 + 另一端，共 12 点）

地形跨越增益是**按序列通过**才生效的（公路 3s、隧道 3s、高地 5s、飞坡 10s），必须按"低→高"或"一端→中间→另一端"顺序触发 RFID 卡，且途中不能检测到其他 RFID 卡。配置表需要支持**有序路径点序列**。

#### ⚠ 4 分钟增强回血窗口参数

规则明确：**比赛开始 4 分钟后**（剩余 ≤ 180s），补给区脱战回血从 10%/s → 25%/s。需暴露 `enhanced_heal_start_elapsed_s` 参数。

#### ⚠ 对方堡垒增益点坐标

`InitSentryConfig` 配了 `fortress_enemy_x/y`，规则说"比赛进行 3 分钟且对方前哨站被击毁后"可占领对方堡垒来触发**对方基地护甲展开**（连续占领 20s），这是一个高价值战术窗口。

getInput("cumulative_instant_count", bb_cum);

输出到黑板: {state.power_boosted} (bool) + {state.power_boost_remain_s} (int)

3.// 虚弱解除沿检测: 上帧虚弱 → 本帧不虚弱 → 无敌窗口(重新)开始
const bool cur_weakness = (!r.shooter_power_output && r.current_hp > 0);
if (prev_weakness_ && !cur_weakness && !cur_dead && now_ms > 0) {
    weakness_dispel_ms_ = now_ms;
}
// 无敌来源: 复活 OR 虚弱解除 → 取最近的时刻
std::uint64_t invincible_start = std::max(respawn_ms_, weakness_dispel_ms_);

规则要点: 复活后无敌最多 30s，但虚弱解除时：

如果无敌已累计 > 10s → 无敌立即解除
如果 < 10s → 保持到满 10s
当前实现简化为 10s 窗口（RESPAWN_INVINCIBLE_MS = 10000），这是保守估计——确保在 10s 内的行为是正确的。

越快解除虚弱 → 无敌保留越长。配合优化建议 3 的"选最近增益点"策略，形成闭环：快速到达最近增益点 → 快速解除虚弱 → 保留更多无敌时间 → 无敌时间内可以更激进行动。
